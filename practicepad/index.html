Watchlist

One problem, three coding parts plus a discussion part. The interviewer reveals each part only when you're done with the last one. Budget: 45 minutes.
Interviewer We've got an internal tool that shows a developer a list of files they care about. The file system is a tree. A user creates a watch, like "show me everything under /src that ends in .py". The screen shows the union of all active watches as one sorted list of paths. I've pasted a FileTree class into the pad with the tree helpers already written. Read it, use it, you don't need to touch it. We'll build the Watchlist class on top.

The sample tree the tests use

/
├── src/
│   ├── main.py
│   ├── util.py
│   ├── README.md
│   └── net/
│       ├── sock.py
│       └── sock_test.py
└── docs/
    ├── guide.md
    └── img/

Part 1 · Make it work

code

Implement Watchlist:

A file is displayed when at least one active watch covers it. A watch covers a file when the file is anywhere in the subtree under the watch's root and its name ends with the watch's extension (no extension means every file).

Example on the tree above: add_watch("/src", ".py") then display() gives
["/src/main.py", "/src/net/sock.py", "/src/net/sock_test.py", "/src/util.py"].

Before you type: say what you're going to do and what you'll store.

Part 2 · Make it fast

code
Finish Part 1 first.
Interviewer So, the UI calls display() on every repaint. Think hundreds of times a second. Watches get added or removed maybe a few times a minute. Right now, what does a call to display() cost? Can we make it cheap?

Also, watches can overlap: someone watches /src and someone else watches /src/net. If I remove the second one, nothing that the first one covers should disappear.

Change your design so display() does no tree walking. The tests check that display() never calls iter_files, that overlapping watches survive each other's removal, and that callers can't corrupt what you hand back.

Say out loud: what was wrong with the old design, what the new invariant is, and what each operation costs now.

Part 3 · The tree changes under you

code
Finish Part 2 first.
Interviewer Files get created and deleted while watches are live. The tree will call you back. Keep the display correct without rebuilding it from scratch.

on_file_added is called right after the node exists in the tree. on_file_removed is called right before it's removed. Ask yourself why that order might matter.

Part 4 · Discussion

no code
Finish Part 3 first.

No more code. Answer each one out loud, with the cost in terms of F files, W watches and D tree depth.

  1. A whole directory gets deleted at once. What's the cheapest correct thing to do?
  2. Now there are 10,000 watches, mostly on deep paths. What does on_file_added cost, and how would you restructure to fix it?
  3. Someone adds a watch whose root is a file, not a directory. What happens in your code? Is that what you want?
  4. Product wants the display ordered by most-recently-changed instead of by path. What changes, and what does it cost now?
  5. Two threads call this class. Name the first thing that breaks.

Interviewer

The questions worth asking, the nudges you'll hear, and what each nudge is actually telling you. Open them one at a time, like a real interviewer would give them to you.

How round 1 actually runs

  • 45–60 minutes on Zoom with a shared pad. Usually one problem that grows in parts, not several problems.
  • Interns get class-building, implementation-style problems with an emphasis on clean code, not algorithm bingo. Jane Street says this themselves: open-ended, several plausible angles, no single "aha".
  • Interviewers may stay quiet. Silence is not a verdict. Narrate anyway.
  • Hints are part of the format. Taking a nudge and running with it is a positive signal, not a point off.
  • They don't need you to finish. They need to watch you work. The journey is graded, not the final snapshot.

Clarifying questions, and the answers you'd get

The nudge ladder

If you hear one of these, your current code has a specific problem. Open the nudge only when you'd have earned it.

Signal decoder

"This function is going to be called a lot."Cache it. Move the work to the rarer operations. Then say the new costs out loud.
"What if these overlap?"A set loses information. Count how many things reference each item: reference counting.
"Do you need to recompute all of that?"Update incrementally from the change, don't rebuild from scratch.
"What's the complexity of that?"Answer in the problem's real sizes (files, watches, depth), not a bare n.
"Is there a simpler way?"You're over-engineering. Step back and say the simplest thing that works.
"Does that handle…?"There's a bug. Trace the example they gave through your code, line by line, out loud.
"How confident are you in that?"They want calibration. "Fairly confident about X, not sure about Y, let me check Y with an example."
"What would you do in production?"Defensive choices: return copies, validate inputs, name the invariant your data structure keeps.

What gets graded

Paraphrased from Jane Street's own prep page and interviewing blog post. The one thing they repeat: the main question is whether they'd want to work with you, and the interview is a simulation of working with you.
  • Be nice. Pleasant, collaborative. Their words: the cleverest person in the world doesn't get hired if they aren't pleasant to talk to.
  • Be clear. Simple and to the point. Use examples. Don't use a term of art you can't define on the spot.
  • Know your language. Write real, idiomatic code without looking things up: loops, classes, dicts, exceptions, sensible organization.
  • Know what you don't know. Say "I'm not sure" rather than guessing. State your confidence in individual assumptions.
  • Write the code you said you would write. Agree on a plan, then execute that plan. Changing plans mid-way without discussion is explicitly called out as a failure mode.
  • Name tradeoffs and pick a side, with a reason. "Clearly describe the most important considerations, lay out a plan, note tradeoffs and explain which side you took and why."
  • Ask thoughtful questions about unclear parts.
  • Engage with hints. Update on what the interviewer tells you.
The failure mode this pad is built around. The code in this problem is trivial for everyone who passes. Deriving the suboptimal-to-optimal path is table stakes, not the differentiator. The differentiator is whether the interviewer could follow your reasoning the whole time without asking. Every time you change the design, say three things: what was wrong, what the new invariant is, what it costs now. If you optimize for "solving", you skip all three.

Sentences that do the work

When you change the design

"The problem with what I have is that display() re-walks every watched subtree on every call, so it's O(F) per call even when nothing changed."

"So the invariant I'll keep is: a path is in the display exactly when its reference count is above zero. Add and remove maintain that; display just reads."

"That moves the cost to add and remove, which are O(size of that subtree) each, and display becomes O(size of display) for the copy. Given the call frequencies you gave me, that's the right trade."

When you're unsure

"I'm fairly confident about the counting. I'm less sure about the removal order in Part 3; let me check it against the example before I commit."

When you take a hint

"Right, that's the overlap case. A set can't tell me whether the file is still covered after one watch goes away. I'll switch the set to a count per path. Everything else stays the same."
